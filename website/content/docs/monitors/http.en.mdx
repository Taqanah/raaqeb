An HTTP monitor sends a request to a URL and judges the response by its success rules: an ordered list of assertions that must all pass. Use it for websites, APIs and health endpoints. For a port that speaks something other than HTTP, use [TCP](/en/docs/monitors/tcp).

## Add an HTTP monitor

Select **Add monitor**, choose **HTTP** as the **Check type**, and fill in the sections below. The fields every check type shares (name, schedule, organization and retention, notifications) are on [Monitors](/en/docs/monitors).

### Monitor

| Field | What it means | Default and limits |
|---|---|---|
| **Method** | The request method. | `GET`. Also `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS`. |
| **URL** | The address to request. | Required. Starts with `http://` or `https://`. An IP address and `localhost` work. A user name or password in the URL is refused: use **Authentication**. |
| **Warn before the domain's registration expires** | Reads the domain's registration once a day and sends the domain expiring event. See [Domain registration](/en/docs/monitors/domains). | On. For a domain name only. |

### Success rules

A check is up when every assertion passes, in order. The first one that fails ends the check and gives its reason; the ones after it are not evaluated. Select **Add assertion** for another row. The rule needs at least one assertion; a new monitor starts with **Status code in** `2xx`.

| Assertion | Fields | Passes when |
|---|---|---|
| **Status code in** | **Status codes** | The status code is in the list. Each entry is a class (`2xx`), a code (`204`) or a range (`200-299`), separated by commas. |
| **Body contains** | **Text** | The body contains the text, case-sensitive. |
| **Body does not contain** | **Text** | The body does not contain the text. |
| **JSON value equals** | **Path, such as data.status**, **Value** | The body is JSON, the path exists, and its value as text equals **Value**. |
| **JSON value matches** | **Path, such as data.status**, **Pattern** | The body is JSON, the path exists, and its value as text matches the regular expression. |
| **Header equals** | **Header name**, **Value** | The response has the header and its value equals **Value** exactly. A missing header fails, even against an empty value. |
| **Response time under** | **Time** (ms) | The response time is below this many milliseconds, 1 to 60000. |

A JSON path is keys separated by dots, with indexes in square brackets: `status`, `data.items[0].status`. Wildcards, filters and slices are not supported. A string value is compared as it is; any other value is compared as JSON text, so a number reads `12`, a boolean `true` and an object `{"a":1}`. A pattern is a JavaScript regular expression with no flags, so add `^` and `$` to match the whole value.

Raaqeb reads at most 1 MB of the body and cancels the rest; the assertions run on what was read, decoded as UTF-8.

### Request

| Field | What it means | Default and limits |
|---|---|---|
| **Request body** | Sent with the request. `GET` and `HEAD` send no body. | Empty. Up to 65536 characters. |
| **Follow redirects** | Follows `301`, `302`, `303`, `307` and `308` responses to their `Location`. Off, the redirect response itself is judged. | On. At most 10 redirects. |
| **Ignore TLS errors** | Accepts expired and self-signed certificates. | Off. |
| **Authentication** | **None**, **User name and password** (basic auth), **Bearer token** or **OAuth 2.0 client credentials**. | None. A user name cannot contain a colon. |
| **Request headers** | Custom headers sent with every attempt. Select **Add header** for another. | Up to 20, each name once. A value is one line of Latin characters. |
| **Proxy** | An `http` or `https` address this monitor's requests go through, in place of the install's [outbound proxy](/en/docs/operate/outbound-proxy), and whatever `NO_PROXY` lists. A proxy that asks for one takes a **Proxy user name** and **Proxy password** under it. | Empty: the install's proxy, if it has one. No user name in the address, and no SOCKS. |

Each check sends `User-Agent: raaqeb/<version>`, with the version of the running build. A **Request headers** entry named `User-Agent` replaces it.

Authentication (a user name's password, a token, an OAuth client secret), request headers and the proxy's user name and password are credentials: Raaqeb stores them encrypted with the install key and never shows their values again. On edit, a saved secret shows "Saved; leave it empty to keep it". A renamed header needs its value typed again. If you set both **Authentication** and a custom `Authorization` header, **Authentication** wins.

When following redirects, a redirect to another origin drops the `Authorization`, `Cookie` and `Proxy-Authorization` headers; other headers go on. A `303`, or a `301` or `302` answering a `POST`, turns the next request into a `GET` with no body. A redirect to anything but `http` or `https` fails the attempt.

### OAuth 2.0 client credentials

For an API that wants a bearer token from an authorization server. Choose **OAuth 2.0 client credentials** under **Authentication**:

| Field | What it means | Default and limits |
|---|---|---|
| **Token URL** | The authorization server's token endpoint, an `http` or `https` address. | Required. No user name or password in the address. |
| **Client ID** | The ID the server gave this client. | Required. |
| **Client secret** | The client's secret. A credential: stored encrypted with the install key and never shown again; leave it empty on edit to keep it. | Required. |
| **Scope** | The scopes to ask for, separated by spaces. | Empty: none sent. |
| **Audience** | The API the token is for, for a server that asks for one, such as Auth0. | Empty: none sent. |
| **Client authentication** | **HTTP Basic**, which sends the ID and secret in the `Authorization` header, or **In the request body**, which sends them as form fields. | HTTP Basic. |

Each check sends the token to the monitor's address as `Authorization: Bearer <token>`, in place of any custom `Authorization` header. Raaqeb asks the token endpoint when the monitor has no token, and keeps the token in memory, one per monitor, until a tenth of its lifetime (at most a minute) before it expires; it asks again after that. A server that names no lifetime gets 5 minutes, and none is kept longer than a day. If the target answers `401` to a token Raaqeb had kept, the token is dropped and the next check asks for another. Nothing is stored: a restart asks again, and the token is never written to the checks, the log or a capture.

The token request goes through the monitor's own proxy, or the install's [outbound proxy](/en/docs/operate/outbound-proxy), and does not follow redirects. **Ignore TLS errors** applies to it; the monitor's CA certificates and client certificate do not, since they are for the target. It shares the check's timeout, so a token endpoint that is too slow reads as "Timed out".

### Certificates

For an API behind mutual TLS, or whose certificate a private authority signed.

| Field | What it means | Default and limits |
|---|---|---|
| **Trusted CA certificates** | PEM text of one or more certificate authorities the check trusts for this monitor's server, in place of the well-known ones. | Empty: the well-known authorities. Up to 64 KB. |
| **Client certificate** | PEM text of the certificate, and any intermediates after it, that the check presents to a server that requires one. | Empty: none. For `https` addresses only. Up to 16 KB. |
| **Private key** | PEM text of the key that belongs to the certificate, encrypted or not. A credential: stored encrypted with the install key and never shown again. | Required with a client certificate. |
| **Key passphrase** | Opens an encrypted key. | Empty: none. |

When you save, Raaqeb checks that the certificate and the CA text are PEM certificates, that the key opens with its passphrase and belongs to the certificate, and refuses the form with the reason if not. The certificates are public, so they come back in the form; the key and passphrase do not: on edit, leave them empty to keep them, or paste a new key to replace both. Remove the client certificate and its key goes with it. **Test now** checks the same and presents the same certificate.

Once **Trusted CA certificates** is set, only those authorities are trusted for this monitor. **Ignore TLS errors** still accepts any server certificate, and the client certificate is still presented. An `http` proxy, the monitor's own or the install's [outbound proxy](/en/docs/operate/outbound-proxy), tunnels the handshake as it does any `https` request, so the server sees the certificate. An `https` proxy does not work with **Trusted CA certificates** or a **Client certificate**: the runtime has no TLS option for the proxy itself, so it would check the proxy with the same CA and hand it the certificate. The form refuses the combination, and a check whose install proxy is an `https` one fails with "Custom CA or client certificate through an https proxy" without sending anything. A redirect to another origin leaves the CA, certificate, key and passphrase behind, since they were set for the first address, and the new address is verified with the well-known authorities.

To try it against your own CA, make a client certificate and paste the files:

```sh
openssl req -newkey ec -pkeyopt ec_paramgen_curve:prime256v1 -nodes \
  -keyout client.key -out client.csr -subj "/CN=raaqeb"
openssl x509 -req -in client.csr -CA ca.pem -CAkey ca.key -CAcreateserial \
  -days 365 -out client.pem
```

### Certificate and capture

| Field | What it means | Default and limits |
|---|---|---|
| **Warn before the certificate expires** | Records the site's certificate and sends the certificate expiring event. See [Certificate record](/en/docs/monitors/certificates). | Off. For `https` addresses only. |
| **Before it expires** | How many days before expiry the first warning goes. | 14 days. 1 to 365. |
| **Capture mode** | When a check keeps the response headers and the first 4 KB of the body: **Off**, **On failure** (down checks only) or **Always**. | Off. **Always** costs about 5.8 MB a day at a 1 minute interval. |

A capture never holds request headers or credentials. `Set-Cookie` and any response header whose name contains `auth`, `token`, `key` or `cookie` keep their name and lose their value. Any credential the check sent that the response repeats is replaced with `[REDACTED]`. The values of the standard request headers `Accept`, `Accept-Encoding`, `Accept-Language`, `Content-Type`, `Cache-Control` and `User-Agent` are not treated as credentials.

## Up, degraded and down

The response time runs from the start of the request to the end of the body read, capped by the timeout.

- **Up**: every assertion passed and the response time is within the degraded threshold.
- **Degraded**: every assertion passed and the response time is above the degraded threshold.
- **Down**: an assertion failed, or the request did not complete, on the last attempt.

The reasons a failed check reports:

| Reason | What happened |
|---|---|
| Timed out | The attempt, body included, took longer than the timeout. |
| DNS lookup failed | The host name did not resolve. |
| Connection refused | Nothing accepted the connection at the host and port. |
| Connection failed | The connection was reset, closed or unreachable, or the TLS handshake ended before any certificate. The code is kept. |
| Certificate expired | The certificate's validity has ended. |
| Token request failed | The token endpoint did not give a token: it answered with an error status, or an answer with no usable access token, or did not answer. Shows its HTTP status and the `error` it named, such as `invalid_client`. The target is not called. |
| Custom CA or client certificate through an https proxy | The monitor has a custom CA or a client certificate and its requests go through an `https` proxy, which the runtime cannot do safely. No request is sent. |
| Client certificate expired | The client certificate is past its end date, or before its start date. No request is sent. |
| Client certificate refused | The server closed the connection while a request that carried a client certificate was setting it up, which is how a server that requires one and does not accept this one answers. The runtime reports a plain reset, so a network reset gives the same reason; the code is kept. |
| Certificate invalid | The certificate did not verify: self-signed, issued for another name, or from an unknown issuer. The code is kept. |
| Unexpected status code | **Status code in** failed. Shows the expected codes and the observed one. |
| An assertion failed | A body, JSON or header assertion failed. Shows the expected and observed values, up to 200 characters each. |
| Slow response | **Response time under** failed. Shows the limit and the observed time. |
| Too many redirects | More than 10 redirects. |
| Unknown error | Anything else. The raw error text is kept beside it. |

With **Ignore TLS errors** on, the two certificate reasons do not happen. The two client certificate reasons still do.

## Example

An API's health endpoint, `https://api.example.com/health`, answers:

```json
{ "status": "ok", "db": { "latency_ms": 12 } }
```

Set **URL** to `https://api.example.com/health`, keep **Status code in** `2xx`, add **JSON value equals** with the path `status` and **Value** `ok`, and set **Degraded threshold** to `800`.

- A `503` response is down with "Unexpected status code", expected `2xx`, observed `503`. The JSON assertion is not evaluated.
- A `200` with `"status": "starting"` is down with "An assertion failed", expected `ok`, observed `starting`.
- A `200` with `"status": "ok"` that takes 1.2 seconds is degraded.

Select **Test now** before saving to see the status code, the response time, the body size, each assertion's result and the response itself.

An install has one or more operator accounts. Onboarding makes the first, and it is the install's owner. Every later account comes from an invitation, and each has one role. The team page, under Install in the sidebar, lists them for an owner or an admin.

## Roles

Each role may do everything the role below it does, and more:

| | Owner | Admin | Editor | Responder | Viewer |
|---|---|---|---|---|---|
| Read monitors, status pages, components, incidents, maintenance and channels | yes | yes | yes | yes | yes |
| Change their own name, email, password, language, sessions and second step | yes | yes | yes | yes | yes |
| Check now, acknowledge an outage | yes | yes | yes | yes | |
| Write incidents and their updates | yes | yes | yes | yes | |
| Schedule, edit, end and cancel maintenance | yes | yes | yes | yes | |
| Change monitors, status pages, components and subscribers | yes | yes | yes | | |
| Delete an incident | yes | yes | yes | | |
| Change notification channels and settings | yes | yes | | | |
| Invite, change, deactivate and remove accounts that are not owners | yes | yes | | | |
| Give or take the owner role, hand ownership on | yes | | | | |
| Export and import | yes | | | | |
| Require a second step of everyone | yes | | | | |

The server checks the role on every call; the admin pages only hide or disable what a role cannot do, with the reason. A page whose record a role cannot change opens read-only.

## Invitations

Invite an operator from the team page with their email and a role. The invitation's link works once, for seven days. Where an email channel exists the link is emailed; it is always shown once on the page so you can copy it and send it yourself. Send an invitation again for a new link (the old one stops working), or revoke it. At most 20 invitations go out an hour.

The person who opens the link chooses a name and a password and is signed in. An address that already has an account cannot be invited.

## Changing, deactivating and removing

- **A role** changes at once; a lower role ends the account's sessions, so it signs in again under it. Giving or taking the owner role asks for your password.
- **Deactivating** ends the account's sessions now and keeps the account; it cannot sign in until it is reactivated.
- **Removing** deletes the account, its sessions and its password for good. Incidents it wrote stay.
- **Handing ownership on** makes another account an owner and you an admin, after your password.

Deactivating or removing an owner asks for your password too. An account that is deactivated, removed or given a lower role takes with it the open invitations it could no longer send.

Nobody changes their own account on the team page, so the last owner cannot leave the install without one. An install may have several owners.

What carries an owner's credentials is an owner's alone: the email channel sign-in mail goes through, the public address that reset links and invitations are built on, the trusted proxies, and single sign-on.

## A second step for everyone

An owner whose own second step is on may require it of every operator, on the sign-in settings page. An operator without one then reaches only their own account until they switch it on.

## Single sign-on

An owner can let operators sign in through one OpenID Connect identity provider (Keycloak, Authentik, Okta, Entra ID, Google Workspace) on the single sign-on settings page:

1. Register Raaqeb with the provider as a web client, with the callback URL the page shows (`https://your-address/api/auth/callback/oidc`), and the `openid`, `email` and `profile` scopes.
2. Paste the provider's discovery URL (it usually ends in `/.well-known/openid-configuration`), the client ID and the client secret. **Test** fetches the discovery document from the server and says whether it names signing keys. The secret is stored encrypted with the install key.
3. Choose who gets an account: only those invited, or also anyone at the domains you list. An invited address takes the invitation's role; one at a listed domain takes the role its claim maps to (`sre = editor`, read from a claim such as `groups`), else the default role. The provider never gives the owner role, and a role is read only when the account is made.

An address that already has an account signs in as it once the provider says the address is verified (`email_verified`); the provider never makes an account for an address it has not verified. A deactivated account is refused.

**Require single sign-on** keeps the password for owners alone, so an owner can still sign in when the provider is down. An invitation for another role is then accepted through the provider. A sign-in through the provider relies on the provider's own second step, so a required second step does not ask for Raaqeb's.

If the provider's discovery document does not answer within five seconds, the button stays and the provider is tried again a minute later; passwords keep working meanwhile.

## The audit log

Owners and admins read the audit log from the sidebar: every change an operator made in the admin area, every sign-in, and every refused sign-in with the email typed or given by your identity provider and why it was refused, newest first, with who, the record, the client address (behind your trusted proxies) and the time. Filter it by account or by kind. An entry keeps what was asked without its secrets (never a password, a key or a token), is never changed, travels in the export, and is deleted once it is older than the install's retention.

## When a password is lost

`raaqeb reset-password <email>` prints a reset link for the account with that email ([commands](/en/docs/operate/commands)). An owner who lost theirs can use it from the server.

## Export and import

An export carries every account with its role, name and preferences, never its password, sessions or second step. An import creates each account the install lacks, without a password: it signs in once a reset link sets one. An account the install already has keeps its own role and password.

التثبيت الذي يصل إلى الإنترنت عبر وكيل وحده يرسل فحوص HTTP والإشعارات والتحقق اليومي من الإصدارات عبر ذلك الوكيل. للتثبيت كله طريق واحد، ولمراقبة HTTP واحدة وكيل خاص بها يحل محله. لا دعم لـ SOCKS، ولا قائمة وكلاء مشتركة تختار منها.

## للتثبيت كله

اضبط `HTTP_PROXY` و`HTTPS_PROXY` على عنوان الوكيل، و`NO_PROXY` على ما يجب ألا يمر به. اضبطها حيث يحفظ التثبيت [إعدادات التشغيل](/docs/operate/boot-settings)، ثم أعد تشغيل راقب:

```sh
HTTPS_PROXY='http://proxy.internal:3128'
HTTP_PROXY='http://proxy.internal:3128'
NO_PROXY='localhost,127.0.0.1,.internal'
```

هذه ليست إعدادات راقب نفسه: تقرؤها بيئة التشغيل عند كل طلب، فلا تظهر في صفحات الإعدادات ولا يطبع راقب قيمها. والوكيل الذي يطلب اسم مستخدم وكلمة مرور تُكتبان في عنوانه، `http://user:password@proxy.internal:3128`. وعنوان الوكيل `http` أو `https`؛ ويحدد المتغير الوكيل بحسب بروتوكول الهدف، فـ`HTTP_PROXY` لهدف `http://` و`HTTPS_PROXY` لهدف `https://`، ويخدم `ALL_PROXY` الاثنين إذا لم يُضبط متغير البروتوكول. وتعمل الأسماء بالأحرف الصغيرة أيضًا. وأي عنوان يسمّي نوعًا آخر من الوكلاء، مثل `socks5://`، يُتجاهل ويخرج الطلب مباشرة.

`NO_PROXY` قائمة مضيفين تفصل بينها فواصل أو مسافات:

| المدخل | ما يطابقه |
|---|---|
| `*` | كل مضيف |
| `example.com` أو `.example.com` أو `*.example.com` | `example.com` ونطاقاته الفرعية |
| `10.0.0.5` أو `::1` | هذا العنوان |
| `10.0.0.0/8` | كل عنوان في النطاق |
| `example.com:8080` | المضيف على هذا المنفذ وحده |

### ما يمر بالوكيل

- فحوص HTTP، عبر الوكيل مباشرة لـ`http`، وعبر نفق يفتحه الوكيل (`CONNECT`) لـ`https`، وكل إعادة توجيه تتبعها، ومع تفعيل «تجاهل أخطاء TLS» كما مع تعطيله. و«اختبر الآن» يسلك الطريق نفسه الذي يسلكه الفحص المجدول.
- قنوات الإشعار التي ترسل عبر HTTP: Webhook وSlack وDiscord وntfy وTelegram.
- Webhook المشترك. يحل راقب اسم مضيفه أولًا ثم يتصل بالعنوان الذي فحصه، فتُطابَق `NO_PROXY` مع ذلك العنوان: اكتب فيها عنوانًا أو نطاق عناوين، فاسم المضيف لا يطابق.
- التحقق اليومي من وجود إصدار أحدث.

### ما لا يمر بالوكيل أبدًا

وكيل HTTP لا ينفع فحصًا لا يتكلم HTTP، ولا يمرّر التثبيت هذه الفحوص عبره:

- مراقبات TCP وDNS وقواعد البيانات (Postgres وMySQL وRedis وMongoDB) تتصل مباشرة، وكذلك المحلل الذي تسمّيه مراقبة DNS.
- مراقبة Docker تسأل الخادوم الخلفي مباشرة: فهو على جهازك أو شبكتك، فلا يُرسل عنوانه إلى الوكيل.
- البريد، قناة البريد وبريد تسجيل الدخول، يُرسل عبر SMTP مباشرة إلى الخادوم الذي اخترته.
- خيار انتهاء الشهادة يقرأ الشهادة عبر اتصال TLS خاص به. وفي شبكة لا مخرج لها إلا الوكيل لا يستطيع قراءتها، وتستمر فحوص المراقبة نفسها.
- `raaqeb health`، وهو يسأل العملية على عنوانها هي.

فالشبكة التي لا تسمح بالخروج إلا عبر الوكيل تحتاج إلى طريق لخوادم هذه الفحوص، أو إلى مراقبات لا تحتاج إليها.

## لمراقبة HTTP واحدة

يجوز أن يكون لمراقبة HTTP وكيل خاص بها: حقل **الوكيل** في قسم **الطلب**، وهو عنوان `http` أو `https`، وتحته، إن كان الوكيل يطلب ذلك، اسم مستخدم وكلمة مرور. يحل محل طريق التثبيت لهذه المراقبة، ولا تسري عليه `NO_PROXY` لأنك طلبت هذا الوكيل لهذه المراقبة. وإذا تُرك فارغًا اتّبعت المراقبة وكيل التثبيت. ويُختم اسم المستخدم وكلمة المرور بمفتاح راقب كبقية بيانات اعتماد المراقبة، ولا يعرض النموذج كلمة المرور ثانية؛ اتركها فارغة لتبقى. ويُرفض العنوان الذي فيه اسم المستخدم: ضعه في حقله.

الوكيل لطلبات المراقبة وحدها. ولا يغيّر قراءة انتهاء الشهادة، فهي مباشرة.

## حين يرفض الوكيل

الوكيل الذي يأبى فتح النفق، أو يطلب تسجيل دخول لم يصله (`407`)، أو يتعذّر الوصول إليه، يُفشل الفحص بالسبب «رفض الوكيل الطلب أو تعذّر الوصول إليه»، لا بفشل الهدف. وتظهر بجانب السبب الحالة التي أجاب بها الوكيل إن أجاب، ويحمل نص الخطأ كلام الوكيل نفسه، مثل `Proxy refused to open a tunnel: 403 Forbidden`. أما طلب `http` العادي فيُسلَّم إلى الوكيل كاملًا، فأي حالة خطأ أخرى يجيب بها الوكيل، مثل `502` حين يتعذّر عليه بلوغ الهدف، سببها «رمز حالة غير متوقع»: فالوكيل ينقل أخطاء الهدف نفسه بالطريقة ذاتها، ولا شيء يفرّق بينهما. وتبلّغ قنوات الإشعار عن إرسالها بالطريقة نفسها. وإذا اشتغلت مراقبة والحقل فارغ ثم فشلت وهو مضبوط فالوكيل هو موضع البحث.

# Remote probes pull over HTTPS, keep a state per location, and an outage needs its locations to agree

A monitor can be checked from more than one location. A location is either the install itself, the main location, or a probe: the same `raaqeb` binary run elsewhere as `raaqeb probe`, with no database, no data directory and no UI. A probe holds a probe token the admin made and showed once; the install keeps only its SHA-256. The probe pulls the monitors assigned to it and pushes its results over HTTPS to a small authenticated API on the install, so every connection starts at the probe and a probe behind NAT or a firewall works. The install keeps each location's latest result in memory as that location's state; the check history keeps one check per run of the monitor, written by the install's own scheduler, whose result is what the locations agree on. An outage opens when at least the monitor's confirmation count of its locations that are answering see it down.

## The parts

- **The probe.** `raaqeb probe` reads `RAAQEB_PROBE_SERVER` (the install's public address) and `RAAQEB_PROBE_TOKEN`, and runs the same check code the install runs (`server/checks/run.ts`) on the same schedule rules (`server/scheduler/schedule.ts`). It opens no database and loads no handler, so it holds the runtime, the check code and its assignments and nothing else. It keeps only the latest result of each monitor until the install takes it, so a probe cut off from the install for hours holds one result per monitor, never a backlog.
- **The protocol, version 1.** Two endpoints under `/api/probe/v1/`, both behind `Authorization: Bearer rqp_<token>`:
  - `GET /api/probe/v1/assignments` answers the probe's own monitors: id, config, interval, timeout, retries, degraded threshold, last change, and the opened credentials of a monitor that shares them. It carries an `ETag`; the probe asks again every 30 seconds with `If-None-Match`, and an unchanged list is a `304` with no body.
  - `POST /api/probe/v1/results` takes up to 1,000 results: monitor id, result, reason code, response time, attempts, status code, the failure detail's parameters and error text, and the check's age. Each result is judged on its own: a reason the install does not know (a newer probe's) reads as unknown, a status code up to 999 is taken as reported, a result that fits no rule is dropped, and past 1,000 the rest are dropped; the answer counts the dropped and names the assignments' current ETag, so a probe learns of an edit at its next push rather than at its next pull. The probe pushes at most 1,000 a time, forgets what the install took or dropped, and logs every answer that is not 200. A push refused whole (no list of results) marks the probe on the locations page.
  - The version is in the path. A change that an older probe cannot read is `/v2/`, served beside `/v1/` for at least one release, and the probe names its build in `raaqeb-version`, which the locations page shows, so an operator sees which probes to upgrade.
- **Clock skew.** A probe never sends a wall-clock time. Each result carries `ageMs`, how long before the push the check started, measured on the probe's monotonic clock (`performance.now()`), and the install places it at its own receipt time minus that age. A probe whose clock is hours wrong reports correct times; the error is the push's one-way network time, under a second on any path a check would trust. A monotonic clock may not count the time a suspended VM slept, so a result held across a suspend reads younger than it is; the probe pushes within a second of a check, so only a result held while the install was out of reach is affected. The probe measures each request's round trip and sends the last one in `raaqeb-round-trip-ms`; the locations page shows it.
- **Location state.** The install holds, in the scheduler's memory, each location's latest result for each monitor that has more than one location. Nothing about it is written to the database: it is replaced within one interval, and after a restart each location's state is unknown until its next result. A location's state is fresh while its result started within twice the monitor's interval plus the longest its check can take (`longestCheckMs`), and after the monitor last changed (an edit, a pause, a resume); otherwise the location's state is unknown. The probe drops a result it holds for a monitor that changed since its check.
- **After a restart** the held states are empty, so for one freshness window after boot a down that fewer locations than the confirmation count decide is not written: the probes have their time to answer before the main location alone can page.
- **No recent result.** A monitor checked from probes alone that none has a recent result for gets no check, and once its latest check is past the freshness window it has no state: the admin shows no recent result, never up or down, and its components keep their last status as a paused monitor's do (a status level cannot be added). "Check now" on it answers at once that no location answers.
- **The verdict.** The monitor's own check is written by the install's scheduler at each of its runs, as before: after its own check when the main location is one of the monitor's locations, at the due time from the held states when it is not. Its result is the verdict of the fresh locations: down when at least `min(confirmation count, fresh locations)` saw it down, degraded when that many saw it degraded or down, otherwise up. Its response time, reason, attempts, status code and failure detail are those of one location whose result is the verdict, the main location when it is one of them, else the first in the monitor's order. A capture is kept only when that location is the main one. With no fresh location there is no verdict, and no check is written for that run.
- **Confirmation.** A result from any location that would change the verdict brings the monitor's next run forward to the next tick, as "check now" does, so the install checks again itself and an agreeing second location opens the outage within seconds, not an interval later. An outage closes when fewer than the needed count still see it down: the rule is the same in both directions. The down notification names the locations that saw it down, by name, in its text and in the webhook's optional `locations` field.
- **A silent probe** makes its location's state unknown, never down. It leaves the count of fresh locations, so a monitor checked from the main location and one probe, needing both, alerts on the main location alone while the probe is silent: a dead probe never hides a real outage. Once it has not been heard from for two minutes the locations page shows it as silent and the channels of the monitors it checks get `probe.silent`, once, then `probe.reporting` when it is heard again. A restart forgets which were told, so one still silent is told again two minutes after boot.
- **What a probe can check.** HTTP, TCP, DNS, Postgres, MySQL and Redis. Not Docker, whose daemon is the install's own host, and not heartbeat, which the install receives itself. A monitor's certificate and domain registration are read by the install alone, and "test now" runs on the install.
- **Credentials.** A monitor's sealed credentials (an HTTP monitor's auth, headers and proxy password, a database monitor's connection URL) stay on the install unless the monitor's own switch, off by default, shares them with its probes. A shared monitor's assignment carries only what its check type sends: an HTTP monitor's auth, headers and proxy user name and password, a database monitor's connection URL. They are opened on the install and sent over the probe's HTTPS connection; the probe holds them in memory only. An HTTP monitor that does not share them is checked by its probes without them. A database monitor cannot be checked from a probe without sharing, since its connection URL is its credential.

## Storage

Per-location check rows were considered and rejected for the floor. Five probes checking 200 monitors every 60 seconds are 1,440,000 checks a day beside the install's own 288,000. At ADR-0005's 68 bytes per head row that is about 98 MB of head table a day on top of today's 20 MB, every read of today's checks (a status page's today cell, a monitor's uptime) reading six times the rows, and sealed days, rollups, the size budget, the export and the chunk format all learning a location column. Per-location state costs one entry per monitor and location, about 1,000 entries for that install, in memory.

What the database gains:

- `probes`: id, name, the token's SHA-256 (unique), created at, and last seen, version and round trip, written at most every 30 seconds per probe so a busy probe is not a write a second.
- `monitor_probes`: the probes a monitor is checked from, one row each, dropped with either side.
- On `monitors`: whether the main location checks it (on by default), its confirmation count (one by default) and whether it shares its credentials (off by default). Every monitor before this change keeps its behaviour exactly: the main location alone, one confirmation, no credentials sent. A monitor whose last probe is deleted is checked from the main location.

The export carries the probes with their token's SHA-256 and each monitor's locations, never a token, so the probes of an install moved to another host keep working with the tokens they hold. A hash does not let anyone sign in as the probe; the file already holds the monitors' credentials in clear and is handled like a backup.

## Security

- **Tokens.** `rqp_` and 32 random bytes in base64url. Only the SHA-256 is stored, and a request's token is found by looking its SHA-256 up in a unique index. The lookup's timing can tell at most whether some stored digest shares a prefix with the digest of the token sent, which says nothing usable about any token: finding a token from its digest is a preimage of SHA-256 over 256 random bits. Making a new token stops the old one at once; deleting the probe stops it and drops its locations from every monitor.
- **Scope.** A token names one probe. The assignments are that probe's monitors alone, and a pushed result for a monitor not assigned to it is dropped. A probe never reads another probe's state, the install's settings, or any monitor's history.
- **Rate limits.** At most 120 requests a minute per probe, and 10 refused tokens a minute per client address (an IPv6 address counts by its /64); past either the answer is `429` with `Retry-After`, which the probe logs. A barred address is refused only for wrong tokens: a probe's own token is always looked up, so probes behind one address (a proxy, CGNAT) never lock each other out. The counts sweep at most once a minute and hold at most 10,000 addresses, the oldest going first. A probe pushes at most once a second and pulls every 30 seconds, well inside the first.
- **No session, no CSRF.** The API takes no cookie and renders nothing, so it is outside the render pace and the CSRF middleware, as the heartbeat and metrics endpoints are.
- **Credentials leave only by opt-in,** per monitor, as above. The probe needs HTTPS to the install for them to be safe in transit; the locations page says so, and the probe refuses an `http` address other than a loopback one.

## Considered options

- **The install pushes work to probes.** Needs a reachable probe, an open port and a second authentication direction. Rejected for pull, which works behind NAT and keeps one direction to secure.
- **A long-lived connection (WebSocket or server-sent events)** for assignments and "check now". Saves the 30-second pull. Rejected for now: one more transport to keep alive through proxies, for a gain the push's answer already gives (the ETag).
- **Per-location check rows.** Rejected above for the floor; the trigger to revisit is a per-location response-time chart, which a per-location rollup could serve without raw rows.
- **The probe's own wall clock.** Rejected for ages: a skewed probe would misplace its checks and every outage it opens.
- **Send sealed credentials by default.** Rejected: a probe runs on a host the install does not control, so a secret travels only where the operator said it may.
- **Silence counts as down.** Rejected: a probe's own network failing would page the team about every monitor it checks.

## Consequences

- A monitor checked from several locations has one history, the verdict's, and a chart of one location's response time at a time; the monitor page shows each location's latest state, response time and when it was checked.
- An outage opens up to the time a second location's result takes to arrive; with the bring-forward, that is one tick plus one check on the install.
- The probe's protocol is a public contract with its own version, documented in the OpenAPI document.
- The install's memory grows with the monitors times their locations and with each pull's answer, not with history.
